**Pi-профиль для разработки на 1С:Предприятие — ASK / PLAN / BUILD, субагенты, MCP, знания проекта и тестовый контур.**

## О проекте

Pi 1C Agent — профиль для [Pi Coding Agent](https://github.com/badlogic/pi-mono), заточенный под реальные 1С-проекты.

Одного знания BSL мало. В рабочей базе нужно понимать, где лежит объект, можно ли менять основную конфигурацию, есть ли расширение, какие правила действуют именно в этом проекте, как получить настоящие метаданные без догадок и что считать готовым результатом: исходники, .cfe, .cf, тест или план.

Pi 1C Agent добавляет этот слой поверх обычного coding agent.

Если коротко: **агент сначала разбирается в проекте, потом планирует, потом меняет код и проверяет результат**. Режим вопросов отделён от записи, знания конкретной конфигурации живут отдельно от общего промпта, а большие задачи можно разложить между специализированными субагентами.

В 0.9 runtime сам собирает короткий system kernel, выбирает структурный MCP до широкого поиска, держит бюджет контекста и включает multi-agent только с нужного tier.

## Возможности

| Что | Как это работает |
|---|---|
| **ASK / PLAN / BUILD** | ASK читает и отвечает. PLAN исследует задачу и готовит план. BUILD меняет файлы и выполняет работу |
| **Путь работы** | `/taskmode` выбирает docs-fix / spec-authoring / analytics / quick-fix / full-cycle / auto. Пин сессии виден в футере рядом с режимом |
| **Работа с 1С-проектом** | Учитывает src/cf, src/cfe, epf, erf, build-артефакты, .dev.env и проектные правила |
| **Выбор контейнера** | Перед изменением определяет, куда писать: в основную конфигурацию или существующее расширение |
| **Метаданные через MCP** | Может получать реальную структуру конфигурации и объектов вместо угадывания имён реквизитов и типов |
| **Субагенты** | Аналитик, explorer, planner, developer, tester, reviewer, architect, fixer и другие роли |
| **Знания проекта** | Хранит проверенные факты и правила конкретной конфигурации в .pi/1c, с evidence и приоритетами |
| **OpenSpec** | Поддерживает spec-driven workflow: исследование → предложение → реализация → проверка |
| **MCP-инструменты** | Подключаются отдельно: 1С MCP bundle, EDT MCP, browser, Windows UI, Vanessa и другие |
| **Vanessa / КД / Humanizer** | Дополнительные скиллы для Vanessa Automation, КД 2/3 и редактуры русского текста |
| **Сборка и перенос** | Выгрузка из ИБ, загрузка в тестовую базу, сборка .cf / .cfe, deploy-and-test |
| **Память** | Опциональная связка Cognee + OpenViking: короткие факты отдельно от развёрнутых отчётов. Ход пишет pending-файл и не ждёт MCP |
| **Продолжение между сессиями** | `/session-rotate` при заполнении контекста создаёт handoff, открывает свежую Pi-сессию и продолжает задачу с сохранённого состояния |
| **Сессия** | Футер из двух русских блоков: «Сессия» и «Среда». Ответ агента слева, сообщение пользователя справа. Щелчок по подписи открывает тот же оверлей, что и команда |
| **Разделы команд** | `/groups` и `Ctrl+Alt+G`: команды Pi, команды профиля, навыки, готовые задания. Имена слэшей те же, подписи в списке русские |
| **Обучение** | `/learning off\|safe\|auto`. После BUILD повторяемая процедура может стать локальным skill. По умолчанию `safe` |
| **ACP** | `pi-1c-acp` отдаёт этот профиль другому агенту по stdin/stdout, без своего HTTP-порта |
| **MCP проекта** | `.pi/mcp.json` перекрывает одноимённый сервер профиля. Правка через `/mcpconfig`, затем `/reload` |
| **Безопасность** | ASK/PLAN ограничивают запись, /approve добавляет подтверждения, /anon отключает память и следы |
| **Диагностика** | /doctor проверяет профиль, CI гоняет typecheck, тесты, public-tree scan и package doctor |

## Что умеет агент

### Разобрать существующую конфигурацию

Можно дать агенту выгрузку и попросить:

- найти реализацию механизма;
- объяснить, откуда берётся значение;
- найти подписки, обработчики, регламентные задания и интеграции;
- проследить цепочку вызовов;
- сравнить основную конфигурацию и расширения;
- разобраться в чужой доработке;
- определить, какой объект реально нужно менять.

В ASK это делается без записи файлов.

### Спланировать доработку до кода

В PLAN агент не должен сразу «накидать решение». Он исследует исходники, проектные знания и доступные MCP, после чего формирует план:

- что меняем;
- в каком контейнере;
- какие файлы и объекты затронем;
- какие есть риски и edge cases;
- как будем проверять результат.

Готовый PLAN можно продолжить в BUILD с тем же контекстом.

### Реализовать изменение

В BUILD агент может менять исходники, создавать артефакты, вызывать инструменты проекта и передавать части задачи субагентам.

Правила проекта имеют приоритет над общими правилами агента. Если в проекте записано «новые объекты только в расширение X», это учитывается до записи кода.

### Работать в мультиагентном режиме

В репозитории есть отдельные роли:

| Агент | Для чего |
|---|---|
| 1c-analytic | требования, сценарии, логика задачи |
| 1c-explorer | исследование проекта и существующей реализации |
| 1c-planner | план изменения |
| 1c-developer | реализация |
| 1c-tester | тестовый сценарий и проверка |
| 1c-code-reviewer | ревью кода |
| 1c-arch-reviewer | архитектурное ревью |
| 1c-architect | проектирование решения |
| 1c-error-fixer | локализация и исправление дефектов |
| 1c-performance-optimizer | производительность |
| 1c-metadata-manager | работа с метаданными |
| 1c-refactoring | рефакторинг |
| 1c-doc-writer | техническая документация |

Read-only роли можно запускать параллельно. Агенты, которые пишут в одно рабочее дерево, идут последовательно, чтобы не устроить гонку изменений.

В TUI субагент — один живой блок: таймер каждую секунду, лог дочерних tool call раскрывается. Дочерняя модель по умолчанию наследуется от родителя; короткое имя роли резолвится (`explorer` → `1c-explorer`).

### Работать с тестовой базой и релизными артефактами

Для типового цикла есть отдельные команды:

<pre>
/loadfrom1cbase
/update1cbase
/deploy-and-test
/build-release
/restore-testbase
</pre>

Если пользователь просит «собрать для переноса» или «собрать в прод», ожидается бинарный .cfe / .cf, а не просто XML-дерево исходников.

### Использовать знания конкретного проекта

Агент не обязан каждый раз заново выяснять одно и то же.

В .pi/1c можно хранить проверенные знания:

- где лежат остатки;
- какое расширение считается целевым;
- какие объекты нельзя менять;
- какие интеграции есть в конфигурации;
- какие локальные правила приняты в команде.

Знание содержит scope, confidence и evidence. Черновик не становится активным сам — его нужно подтвердить.

## Как проходит задача

~~~mermaid
flowchart LR
    U["Задача пользователя"] --> A{"Режим"}

    A -->|ASK| Q["Исследование<br/>без записи"]
    A -->|PLAN| P["Исходники + MCP +<br/>знания проекта"]
    A -->|BUILD| B["Реализация"]

    P --> T["План:<br/>объекты · файлы · риски · проверка"]
    T --> B

    B --> S{"Нужны<br/>субагенты?"}
    S -->|да| R["Explorer / Developer /<br/>Tester / Reviewer / Fixer"]
    S -->|нет| C["Изменения"]

    R --> C
    C --> V["Проверки / тесты / сборка"]
    V --> D["Готовый результат"]
~~~

Здесь нет схемы «попросил — модель сразу написала код». Исследование, планирование, запись и проверка разделены.

## Продолжение работы при заполнении контекста

Длинная задача не обязана упираться в compaction или обрываться из-за заполненного context window.

В Pi можно включить автоматическую ротацию сессии:

<pre>
/session-rotate on
</pre>

По умолчанию функция выключена. Стандартный порог — **85% контекста**; его можно изменить:

<pre>
/session-rotate 80
/session-rotate status
/session-rotate off
</pre>

Когда порог достигнут, агент завершает текущий turn, формирует handoff с состоянием задачи и проверяет, что он действительно записан. После этого Pi открывает **новую сессию, связанную с предыдущей**, передаёт ей kickoff со ссылкой на handoff и продолжает работу уже в свежем контексте.

Схема выглядит так:

~~~mermaid
flowchart LR
    A["Текущая сессия"] --> B{"Context ≥ threshold?"}
    B -->|нет| A
    B -->|да| C["Остановить новые tool calls"]
    C --> D["Записать handoff"]
    D --> E["Проверить handoff"]
    E --> F["Открыть новую Pi-сессию"]
    F --> G["Передать kickoff + handoff"]
    G --> H["Продолжить ту же задачу"]
~~~

Для пользователя это выглядит как продолжение одного рабочего потока, но технически между сессиями есть граница: текущий turn аккуратно завершается, затем задача продолжается в новой сессии. Это **Pi-only** механизм; он не гарантируется в Cursor.

Если handoff не записался или новая сессия недоступна, ротация не делает вид, что всё прошло успешно: она останавливается и оставляет обычный compaction доступным.

## Режимы работы

### ASK

<pre>/mode ask</pre>

Режим по умолчанию для новой Pi-сессии. Подходит, когда нужно разобраться в коде, найти причину ошибки, изучить архитектуру или проверить гипотезу.

Запись файлов отключена.

### PLAN

<pre>/mode plan</pre>

Подходит перед нетривиальной доработкой.

PLAN исследует проект и готовит planning-артефакты, но не меняет рабочий код. Готовый план содержит:

- Plan;
- ожидаемые файлы и объекты;
- риски и edge cases;
- способ проверки.

### BUILD

<pre>/mode build</pre>

Рабочий режим для реализации: изменение файлов, сборка, deploy, тесты и другие разрешённые действия.

Переключение ASK → PLAN → BUILD доступно командой или Ctrl+Alt+P.

## Путь работы

<pre>/taskmode</pre>

`/taskmode` задаёт, как вести эту сессию. Это не `/mode`: ASK, PLAN и BUILD остаются на месте, syntaxcheck изменённого BSL и триггеры повышения до full-cycle тоже.

Пустой вызов открывает оверлей. Выбранный путь виден в футере.

| Путь | Что это |
|---|---|
| docs-fix | только текст: структура, ссылки, согласованность. Проверки BSL не запускаются |
| spec-authoring | требования и план. Факты 1С подтверждаются, код пишется позже |
| analytics | объяснить или сравнить. Исходники не меняются |
| quick-fix | одна локальная правка, короткий план и нужные проверки |
| full-cycle | требования, реализация, проверка результата и ревью |
| auto | снять метку. Дальше путь выбирается по задаче |

## Сессия в терминале

Футер собран двумя группами.

«Сессия»: режим (Вопрос, Планирование, Реализация), путь, доступ, глубина, экономия, интерфейс, обучение.

«Среда»: проект, граф / код / ИБ, заполнение контекста, модель, число MCP, мышление, ротация, захват, открытые изменения OpenSpec, вид базы и ветка git. На узком терминале прячутся второстепенные подписи. Режим остаётся.

Чат идёт парами рамок: ответ агента слева, сообщение пользователя справа.

`/groups` и `Ctrl+Alt+G` открывают четыре раздела: команды Pi, команды профиля, навыки, готовые задания. Выбор `/mode`, `/learning`, `/init`, `/mcpconfig` и других переключателей сразу открывает их оверлей. Остальные команды вставляются в строку ввода и сами не запускаются. Поиск предыдущего совпадения в транскрипте Pi остаётся на `Ctrl+Shift+G`.

## Быстрый старт

### Требования

- **Node.js 22.19+**
- **Pi Coding Agent 0.85.x**
- Windows, Linux или macOS
- Git
- для работы с ИБ — установленная платформа 1С и доступ к нужной базе
- MCP, Docker, память, Vanessa и browser-инструменты не обязательны и подключаются отдельно

### 1. Клонировать профиль

Linux / macOS:

~~~bash
git clone https://github.com/z03ps00/pi-1c-agent.git ~/pi-1c-agent
~~~

Windows PowerShell:

~~~powershell
git clone https://github.com/z03ps00/pi-1c-agent.git "$HOME\pi-1c-agent"
~~~

Архив релиза `pi-1c-agent-<version>-client.zip` — тот же профиль без тестов, CI и истории git. Node и Pi ставятся отдельно. Распакуйте его и переходите к setup, подставив каталог распаковки вместо клона.

### 2. Выполнить setup

Переменную `PI_CODING_AGENT_DIR` задают только на время setup. Её нельзя записывать в `~/.bashrc`, `~/.profile`, `~/.zshrc` и в пользовательские переменные среды Windows. Иначе каждый запуск `pi` станет агентом 1С, а прежний профиль Pi пропадёт.

Linux / macOS:

~~~bash
PI_CODING_AGENT_DIR="$HOME/pi-1c-agent" node "$HOME/pi-1c-agent/scripts/setup.mjs"
~~~

Windows:

~~~powershell
$env:PI_CODING_AGENT_DIR = "$HOME\pi-1c-agent"
node "$env:PI_CODING_AGENT_DIR\scripts\setup.mjs"
Remove-Item Env:PI_CODING_AGENT_DIR
~~~

Setup прописывает пакет в `settings.json` этого клона и создаёт локальные `auth.json` / `trust.json` из примеров, если их ещё нет. Повторный запуск безопасен. Файл `~/.pi/agent` и любой другой профиль Pi он не трогает.

### 3. Отдельный запуск, не профиль по умолчанию

Профиль 1С запускают своей командой. Обычная команда `pi` остаётся тем профилем, который был до установки.

Linux и macOS — ссылка в `~/.local/bin` (каталог должен быть в `PATH`; на macOS при необходимости добавь его в `~/.zprofile` одной строкой `export PATH="$HOME/.local/bin:$PATH"`, без `PI_CODING_AGENT_DIR`):

~~~bash
chmod +x "$HOME/pi-1c-agent/scripts/pi-1c"
mkdir -p "$HOME/.local/bin"
ln -sfn "$HOME/pi-1c-agent/scripts/pi-1c" "$HOME/.local/bin/pi-1c"
~~~

Windows — `scripts/pi-1c.cmd` уже держит профиль только на свой запуск. Положи его в каталог из `PATH`, не в переменные среды пользователя:

~~~powershell
$bin = "$env:LOCALAPPDATA\Programs\pi-1c"
New-Item -ItemType Directory -Force -Path $bin | Out-Null
Copy-Item "$env:USERPROFILE\pi-1c-agent\scripts\pi-1c.cmd" "$bin\pi-1c.cmd" -Force
$machinePath = [Environment]::GetEnvironmentVariable('Path', 'User')
if ($machinePath -notlike "*$bin*") {
  [Environment]::SetEnvironmentVariable('Path', "$bin;$machinePath", 'User')
}
~~~

Дальше `pi-1c` из папки проекта 1С или `pi-1c /путь/к/проекту`. Если первый аргумент — существующий каталог, лаунчер открывает агента в нём и не передаёт этот путь в `pi`. Путь вида `/…`, `~/…`, `./…`, `../…` или с буквой диска, которого нет, даёт ошибку. Флаги и текст (`pi-1c -c`) уходят в `pi` без смены каталога. Из той же папки `pi` открывает прежний профиль. Новый терминал Windows подхватит `PATH` после перезапуска.

### 4. Ярлык на рабочем столе

Ярлык открывает панель управления этого профиля (`scripts/pi-1c-ctl` / `scripts/pi-1c-ctl.cmd`): статус, новый чат, открыть проект по пути, сессии, модели, диагностика, backup `settings.json`, обновление Pi. В shell rc и в переменные среды пользователя `PI_CODING_AGENT_DIR` не пишется. Команда `pi-1c` по-прежнему запускает агента без панели.

Linux — шаблон `scripts/Pi-1C-Agent.desktop.in`, в `Exec` абсолютный путь к `scripts/pi-1c-ctl`, `Terminal=true`. Если есть каталог ярлыков агентов (`~/Рабочий стол/Программы/AGENTS`, `~/Desktop/Программы/AGENTS` или тот же каталог на рабочем столе), положи `Pi-1C-Agent.desktop` туда. Иначе — на рабочий стол (`xdg-user-dir DESKTOP`) и копию в `~/.local/share/applications/`.

~~~bash
ctl="$HOME/pi-1c-agent/scripts/pi-1c-ctl"
desktop_dir="${XDG_DESKTOP_DIR:-$(xdg-user-dir DESKTOP 2>/dev/null || true)}"
agents_dir=""
for candidate in "$HOME/Рабочий стол/Программы/AGENTS" "$HOME/Desktop/Программы/AGENTS" "$desktop_dir/Программы/AGENTS"; do
  if [ -n "$candidate" ] && [ -d "$candidate" ]; then agents_dir="$candidate"; break; fi
done
chmod +x "$ctl"
sed "s|@PI_1C_CTL@|$ctl|" "$HOME/pi-1c-agent/scripts/Pi-1C-Agent.desktop.in" > /tmp/Pi-1C-Agent.desktop
chmod +x /tmp/Pi-1C-Agent.desktop
if [ -n "$agents_dir" ]; then
  cp /tmp/Pi-1C-Agent.desktop "$agents_dir/Pi-1C-Agent.desktop"
else
  desktop_dir="${desktop_dir:-$HOME/Desktop}"
  mkdir -p "$desktop_dir" "$HOME/.local/share/applications"
  cp /tmp/Pi-1C-Agent.desktop "$desktop_dir/Pi-1C-Agent.desktop"
  cp /tmp/Pi-1C-Agent.desktop "$HOME/.local/share/applications/Pi-1C-Agent.desktop"
fi
~~~

macOS — файл `Pi 1C Agent.command` на рабочем столе. Двойной щелчок открывает Terminal и панель профиля 1С:

~~~bash
desktop="$(osascript -e 'POSIX path of (path to desktop folder)' | tr -d '\r')"
cat > "${desktop}Pi 1C Agent.command" <<EOF
#!/bin/bash
clear
exec "$HOME/pi-1c-agent/scripts/pi-1c-ctl"
EOF
chmod +x "$HOME/pi-1c-agent/scripts/pi-1c-ctl" "${desktop}Pi 1C Agent.command"
~~~

Windows — ярлык `.lnk` на рабочем столе. Цель — `scripts\pi-1c-ctl.cmd`:

~~~powershell
$desktop = [Environment]::GetFolderPath('Desktop')
$target = "$env:USERPROFILE\pi-1c-agent\scripts\pi-1c-ctl.cmd"
$shell = New-Object -ComObject WScript.Shell
$link = $shell.CreateShortcut((Join-Path $desktop 'Pi 1C Agent.lnk'))
$link.TargetPath = $target
$link.WorkingDirectory = "$env:USERPROFILE\pi-1c-agent"
$link.WindowStyle = 1
$link.Description = 'Панель управления Pi 1C Agent'
$link.Save()
~~~

Если файл иконки уже есть (`~/.local/share/icons/pi-1c-agent.svg` на Linux и macOS), в `.desktop` можно добавить строку `Icon=` с этим путём. Без иконки ярлык всё равно запускается.

<pre>/doctor</pre>

## Инициализация проекта

/init — не просто генератор папок.

Сначала мастер открывает оверлей источника: пустой scaffold, существующая ИБ, `.cf`, `.cfe` или `.dt`. Рекомендуемый режим заполнения — стандартный: агент сам собирает платформу и общие настройки с соседних проектов, показывает список и ждёт «Всё верно». Подробный опрос всех переменных остаётся как `/init advanced`. В зависимости от сценария он может настроить:

- пути платформы;
- параметры ИБ;
- структуру src/ и build/;
- префикс и данные разработчика;
- Configuration Knowledge Layer;
- OpenSpec;
- Vanessa;
- КД 2 / КД 3;
- Humanizer RU.

Секретные значения остаются локально. Выбранные extras подключаются только после Apply.

Если проект уже существует и нужен только слой знаний:

<pre>/init knowledge</pre>

## Знания и правила проекта

Приоритет контекста такой:

<pre>
PROJECT rules / preferences
        ↓
CONFIGURATION rules / preferences
        ↓
verified CONFIGURATION facts
        ↓
base 1C rules
</pre>

Так знания по конкретной конфигурации не приходится запихивать в один огромный prompt.

### Добавить знание

<pre>/learn в ERP 2.5 остатки лежат в РегистрНакопления.ТоварыНаСкладах</pre>

Сначала создаётся черновик. Активировать его можно отдельно:

<pre>/learn approve</pre>

### Проанализировать конфигурацию

<pre>
/mode plan
/config analyze архитектура, подсистемы, обмены
</pre>

Агент исследует исходники и предлагает факты/правила с evidence.

### Обновить знания после обновления конфигурации

<pre>
/mode plan
/config update 2.5.28
</pre>

Система сравнивает fingerprint исходников и предлагает:

- invalidate — что устарело;
- update — что нужно уточнить;
- add — что появилось нового.

Изменения вступают в силу только после ревью и /config apply.

## MCP

MCP в профиле **opt-in**. Дефолтный mcp.json не поднимает сервисы автоматически.

Pi читает `mcp.json` профиля и `.pi/mcp.json` текущего проекта. Одинаковое имя сервера в проекте перекрывает профиль. `/init` и `/init knowledge` создают пустой `.pi/mcp.json`, если файла ещё нет, и оставляют существующий как есть.

<pre>
/mcpconfig
/installtools
</pre>

`/mcpconfig` без аргумента выбирает локальный или глобальный файл, затем добавляет или убирает один сервер. После записи нужен `/reload`. Токены в `.pi/mcp.json` не хранят.

Отдельные установщики:

| Команда | Интеграция |
|---|---|
| /installmcp | основной 1С Docker MCP bundle |
| /install-memory-mcp | Cognee + OpenViking |
| /install-edt-mcp | EDT MCP |
| /install-agent-browser | browser для web-client сценариев |
| /install-windows-mcp | Windows desktop UI, когда без него никак |
| /install-vanessa-mcp | Vanessa Automation MCP |

Фрагменты конфигурации лежат в mcp.optional/.

## Humanizer RU

Humanizer RU нужен для русских инструкций, статей, писем, ТЗ и README, которые после генерации звучат слишком «нейросетево».

Он не пытается обмануть AI-detector. Его задача — убрать то, что мешает читать:

- пустые зачины;
- канцелярит;
- безличный пассив;
- маркетинговую накачку;
- обёртки чат-бота;
- стены текста.

Факты, 1С-термины и авторский голос сохраняются. Для текстов владельца проекта в репозитории есть отдельный voice profile.

## Память

Память по умолчанию выключена.

<pre>/install-memory-mcp</pre>

Используются два бэкенда:

| Бэкенд | Для чего |
|---|---|
| **Cognee** | короткие факты, решения, предпочтения, уроки из ошибок |
| **OpenViking** | развёрнутые отчёты, процедуры, handoff и документация |

Перед записью данные проходят redaction секретов. Ход агента пишет файл в `state/agent-memory/pending/` и запускает фоновый воркер, не дожидаясь Cognee и OpenViking. Воркер переживает закрытие сессии, вызывает MCP и переносит запись в `done/` только после проверки recall. `/memory-flush` стартует воркер и сразу возвращает управление.

### Анонимный режим

<pre>
/anon 1
/anon 2
/anon 3
/anon off
</pre>

- 1 — не писать в память;
- 2 — не читать и не писать;
- 3 — дополнительно не создавать локальные handoff-трейсы.

Субагент получает тот же уровень `/anon`, что и родительская сессия.

## Approval mode

<pre>
/approve off
/approve safe
/approve strict
</pre>

- off — без дополнительных подтверждений;
- safe — подтверждать опасные BUILD-действия;
- strict — подтверждать каждый tool call.

Это Pi-only механизм. Cursor читает AGENTS.md как инструкции, но Pi-runtime gates там не работают так же, как в Pi.

## Обучение

<pre>
/learning off
/learning safe
/learning auto
</pre>

Пустой вызов открывает оверлей. Значение хранится в профиле. По умолчанию **safe**. В футере это строка «Обучение».

После законченного хода в BUILD Pi может разобрать повторяемую процедуру и записать локальный skill в `state/evolution/learned/`. В режиме `safe` такой skill ждёт `/evolve approve`. В режиме `auto` включается только procedure-skill без опасных инструментов. Факты, правила, workflows и уроки остаются черновиками. В Cursor этот разбор не запускается.

## ACP

`scripts/pi-1c-acp` и `scripts/pi-1c-acp.cmd` поднимают этот профиль как процесс [Agent Client Protocol](https://agentclientprotocol.com/) v1. Сообщения идут JSON-RPC по stdin и stdout. Свой HTTP-порт процесс не открывает. Лаунчер выставляет `PI_CODING_AGENT_DIR` на клон профиля и стартует `pi --mode rpc`. Слэш-команды те же, что в TUI. Каталог проекта приходит в `session/new`. Один процесс держит одну сессию.

В OpenClaw встроенное имя `pi` запускает обычный Pi. Для этого профиля нужна отдельная запись с именем `pi-1c`. Пример и передача аргументов оверлея: [packages/pi-1c-agent/docs/acp.md](packages/pi-1c-agent/docs/acp.md). Пустой оверлей в ACP отменяется сразу: в тексте задачи пишут `/init from-cfe` или `/mode build`.

## Типовые сценарии

### Разобраться, почему не работает код

<pre>
/mode ask
Разбери, откуда вызывается этот обработчик и при каких условиях сюда попадём.
</pre>

Агент читает исходники, ищет связанные объекты и может обращаться к MCP, но проект не меняет.

### Подготовить план доработки

<pre>
/mode plan
Нужно добавить проверку перед проведением документа. Изучи текущую реализацию и предложи план.
</pre>

На выходе — целевой контейнер, конкретные файлы/объекты, риски и проверка.

### Реализовать задачу с ревью

<pre>
/mode build
Выполни согласованный план. После реализации передай изменения tester и code-reviewer.
</pre>

Для большой задачи исследование, разработку, тестирование и ревью можно развести по отдельным субагентам.

### Поднять проект из существующей базы

<pre>
/mode build
/init
</pre>

Выберите existing infobase, настройте доступ, проверьте preview и примените.

### Собрать артефакт для переноса

<pre>/build-release</pre>

Результат — .cf / .cfe, а не копия XML-исходников.

## Безопасность

В профиле несколько независимых слоёв:

- новая сессия стартует в ASK;
- ASK не пишет файлы;
- PLAN не меняет рабочий код;
- перед изменением определяется целевой контейнер;
- проектные знания активируются только после отдельного approve;
- секреты не должны попадать в knowledge, handoff и память;
- память делает redaction перед записью;
- /approve safe|strict добавляет подтверждение действий;
- /anon отключает memory/traces для чувствительных задач.

Это не отменяет тестовую базу, резервные копии, Git и ревью перед Production.

## Важные ограничения

- MCP-сервисы не считаются установленными только потому, что профиль умеет с ними работать.
- Cursor читает правила профиля, но runtime-защиты ASK/PLAN/APPROVE реализованы именно в Pi.
- Новое расширение не создаётся автоматически — нужен явный запрос.
- Память выключена по умолчанию.
- Агент не должен придумывать метаданные, если их можно проверить по исходникам или MCP.
- Production всё равно требует человеческого ревью и проверки на тестовой базе.
